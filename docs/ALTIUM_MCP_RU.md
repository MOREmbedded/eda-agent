**Почему MCP может запуститься без открытия PCB-проекта**

Здесь два процесса: Python MCP-сервер общается с клиентом по stdio, а DelphiScript внутри Altium выполняет обращения к API редактора. Запуск Python не означает ни открытия PCB-проекта, ни успешной связи с Altium. `app_get_status` может обнаружить процесс через Windows и без работающего DelphiScript. Связь с внутренним скриптом подтверждается ответом `application.ping`.

Python записывает запрос `request_<id>.json`, DelphiScript читает его и пишет `response_<id>.json`; длительные операции могут выдавать `progress_<id>.json`. На этой машине каталог обмена — `C:\Users\Alex\EDA Agent\workspace`, указатель на него — `C:\ProgramData\eda-agent\workspace-path.txt`. Для диагностики полезны `activity.log` и `bridge_trace.log`.

В ходе аудита modem проект уже находился в workspace Altium. Затем явно загружены его девять листов и сфокусирована нужная основная PCB. Проверки DRC/ERC выполнены в настоящем Altium. Чтение файлов использовалось дополнительно для OutJob, variant links и таблиц соответствия выводов.

**Запуск внутреннего скрипта через COM**

Проверенный вызов:

```powershell
$edaScriptProject = 'D:\AI\eda-agent\scripts\altium\Altium_API.PrjScr'
$edaScriptUri = "dxpprocess://ScriptingSystem:RunScript?ProjectName=$edaScriptProject|ProcName=Dispatcher.pas>StartMCPServer"
$edaShell = New-Object -ComObject Shell.Application
$edaShell.ShellExecute($edaScriptUri, '', '', 'open', 0)
```

Это COM-объект **Windows Shell.Application**, который вызывает зарегистрированный в Altium обработчик `dxpprocess` и процесс `ScriptingSystem:RunScript`. Объекты схемы/платы затем доступны DelphiScript через Altium API. Этот способ не доказывает существование отдельного публичного COM ProgID `Altium.Application` с методами редактирования PCB.

Добавлен запускатель с тем же механизмом:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'D:\AI\eda-agent\scripts\start-altium-bridge.ps1' -PrintOnly
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'D:\AI\eda-agent\scripts\start-altium-bridge.ps1'
```

На этой машине выполнение `.ps1` по умолчанию запрещено. Здесь `ExecutionPolicy Bypass` относится только к запускаемому процессу PowerShell и не меняет политику системы. Альтернатива — выполнить COM-строки выше непосредственно в PowerShell. Синтаксис запускателя и режим `-PrintOnly` проверены.

Для своего скрипта укажите существующий `.PrjScr`, содержащий Pascal-модуль и процедуру без аргументов:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'D:\AI\eda-agent\scripts\start-altium-bridge.ps1' `
  -ScriptProject 'D:\AI\MyScripts\MyScripts.PrjScr' `
  -Procedure 'MyUnit.pas>Run'
```

Это шаблон вызова пользовательской процедуры; фиктивный `MyScripts.PrjScr` в ходе аудита не создавался и не запускался. COM-вызов отправляет запрос, но сам по себе не подтверждает завершение процедуры. Для мостового скрипта проверьте ping, для своего — заранее предусмотренный файл результата или другой явный признак завершения.

Не запускайте второй скрипт, пока Altium выполняет первый. После правки Pascal дождитесь завершения запроса, закройте форму `EDA Agent MCP`, отправьте `Ctrl+F3` главному окну Altium, затем выполните запуск и проверьте `script_version`. При окне ошибки сначала прочитайте/закройте его и остановите исполнение. Используйте скрипты из этого checkout; старая копия в `%USERPROFILE%\EDA Agent\scripts` может загрузить другие units. См. **Выявленные особенности достоверности**

`pcb_get_clearance_violations` читает материализованные объекты нарушений, включая исключения. Это не свежий DRC; ответ уже помечен `stale_possible`. `pcb_get_unrouted_nets` и статистика платы считают `eConnectionObject`; `connectivity_rebuilt=true` означает лишь отсутствие исключения при отправке `PCB:UpdateConnectivity`. Исходник `PCBGeneric.pas` прямо говорит, что это не подтверждение пересчёта. На проверяемой плате получено 317 таких объектов при нуле активных unrouted в свежем DRC; нельзя выдавать этот счётчик за 317 доказанных обрывов.

Исправлено `pcb_get_fab_stats`: сравнение объектов `StartLayer/StopLayer` с константами слоёв заменено на `LowLayer/HighLayer`. Результат на настоящей плате изменился с ошибочных 991 buried на 991 through; совпадает с отдельным перечнем via и drill layer pairs. В `pcb_get_vias` добавлены `hole_size_mm` и `size_mm`, прежние целочисленные поля mil сохранены. В этой плате уточнённые значения — около 0.100000 и 0.449999 мм.

Проверки изменения: Pascal lint — 11 файлов, 0 ошибок, 0 предупреждений; загрузка версии `2026.09.05.1` через COM; ping без cast errors; 991 черезотверстие в живом API; проверка числовых новых JSON-полей и совместимости округлённых значений; `git diff --check`. Геометрия и электрические данные PCB не редактировались.

Полный экспорт геометрии этой платы занимал около 150 секунд и блокировал GUI до завершения. Не принимайте превышение обычного тайм-аута за аварийное завершение: проверьте progress и trace, не отправляйте дублирующий экспорт и не перезапускайте мост посреди обработчика. `doctor` и `detach_from_altium` могут сохранять документы; не используйте их как безусловно безопасные операции чтения.

**Ошибки и остановка отладчика**

Запуск через COM не меняет поведение отладчика Altium и не исключает остановку на проблемной строке. Сам скриптовый проект загружается в Altium по пути из URI; ручное открытие его вкладки не требуется.

Обработчики возвращают ожидаемые ошибки как JSON с `success=false`. В `Dispatcher.pas`, около строки 154, вызов `ProcessCommand` дополнительно обёрнут в `try/except`: перехватываемое исключение превращается в `INTERNAL_ERROR`. Текущее общее сообщение содержит имя команды, но не гарантирует текст исходного исключения или стек. Результат записывается в response-файл и лог; после такой обработанной ошибки цикл может принимать следующие запросы.

Ошибка компиляции, остановка на breakpoint или ошибка, перехваченная самим движком/отладчиком Altium до входа в Pascal `except`, может остановить весь polling loop. Python не способен продолжить её посредством файлового IPC. Он проверяет блокирующие окна во время ожидания и возвращает диагностическую ошибку, а при отсутствии ответа — сведения о timeout/состоянии моста. `app_get_script_errors`, `app_list_open_dialogs` и Windows UI-команды не зависят от polling loop; они могут прочитать файл/строку/символ, если Altium показывает эти данные в доступном окне. Одна лишь подсветка строки без диагностического окна не гарантирует их автоматического извлечения.

Восстановление: сохранить диагностику, исправить причину в Pascal, остановить скрипт (`Ctrl+F3`; при модальном окне сначала обработать его), заново запустить через COM и проверить ping/версию. Автоматического продолжения с ошибочной строки здесь нет. Прерывание команды редактирования также не означает автоматического отката: перед повтором необходимо проверить, какие изменения успели примениться. Глобальные настройки остановки отладчика в этом аудите не менялись.
